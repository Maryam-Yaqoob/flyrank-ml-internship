FlyRank ML Internship · Capstone Paper

Can the first half of a month warn you about the second?

Early-warning decline detection for search content — Growth / Recovery / Momentum Prediction, freestyle lane.

Author Maryam Yaqoob Data fact_content_daily_performance · month=2026-03 Repo github.com/Maryam-Yaqoob/flyrank-ml-internship
Section 00

Abstract

Can a (client, content) page's first-half-of-month search activity flag, before the month ends, that it is on track to lose more than 20% of its impressions in the second half? Using fact_content_daily_performance (month=2026-03) from the FlyRank ML Internship warehouse — 9,841,378 rows across 55 clients, aggregated into 151,981 (client, content) pairs with a 32.7% base decline rate — this project compares a transparent CTR-vs-position rule (Precision@10 = 50.0%, not client-held-out) against a Logistic Regression / Random Forest pair trained on five first-half-only features and evaluated on clients neither model ever trained on. The client-held-out model reaches a measured Precision@10 of 40.0% (Logistic Regression) against a 32.7% base rate. The output is a ranked, reason-coded review queue — decision support for a content/SEO team with a fixed review budget, not an automated action or a claim about search-engine mechanics.

Section 01

Problem framing

Which pages should a content team check this sprint, before the drop shows up in an end-of-month report?

Decision supported: given a fixed content-review budget, which (client, content) pages should a content/SEO lead check this sprint? Unit of analysis: one (client, content) pair's activity within March 2026, split into a first-half feature window (Mar 1–15) and a second-half label window (Mar 16–31). Output: a ranked queue, sorted by predicted probability of is_declining_next_half, each row carrying a plain-language reason code and a suggested action. The human action: a person reviews the page — nothing here is automated. Cost of a wrong call: a false positive is a wasted review, cheap and recoverable; a false negative is a real decline that goes unreviewed until it already shows up in a monthly report — the more expensive direction, which is why the primary metric is Precision@10 rather than raw accuracy.

Why ML over a fixed rule: a hand-written rule was tried first — "flag pages with real volume whose CTR is below what their position tier typically gets." It beats the base rate (50.0% vs 32.7% Precision@10), but both signals it leans on came back MIXED when tested directly: CTR did not decrease cleanly by position tier, and decline rate did not decrease cleanly by volume tier. A single hand-written AND/OR rule isn't cleanly separating the pattern — the concrete case for a model that can combine several weak, non-monotonic signals.

Section 02

Data safety

Source: FlyRank ML Internship warehouse (gated, Hugging Face, Parquet), queried directly via DuckDB — never downloaded locally. Table: fact_content_daily_performance, partition month=2026-03 (a mid-panel month; the sealed final-month _sample table was never touched). Grain confirmed unique (report_date × client_hash_id × content_hash_id, 0 duplicates).

Features used — five, all Mar 1–15 only: impressions_first_half, clicks_first_half, ctr_first_half, avg_position_first_half, active_days_first_half.

Excluded on purpose: impressions_second_half — the exact raw material the label is built from (a leakage trap confirmed this: training with it included made the score jump unrealistically). Any pre-computed FlyRank scoring column, so the model learns a pattern rather than reproducing FlyRank's own prior judgment. client_hash_id / content_hash_id — used only to build the client-grouped train/test split, never as model inputs.

No client-identifying details, raw tokens, or private query output appear anywhere in this repo's work/ folder.

Section 03

Baseline

A page is worth reviewing for CTR if it already has real search visibility (impressions_first_half ≥ 50) but its click-through rate sits below what pages at its own position tier typically get. No fitted weights — a transparent, hand-coded rule, scored on the whole month (not client-held-out).

The rule clears the base rate, but both signals it depends on tested as MIXED — real evidence the pattern needs more than one hand-picked feature.

Section 04

Model & analysis

Method: Logistic Regression first — a coefficient-per-feature model, readable in one sentence per feature, the honest floor for "can a straight line through 5 features beat the rule?" — then Random Forest, which adds non-linear splits and feature interactions the rule can't express.

Target: is_declining_next_half = 1 if a pair's summed impressions in Mar 16–31 are more than 20% lower than Mar 1–15, else 0 — an observed future-window outcome, never a same-window bucket.

Section 05

Evaluation

Split: grouped by client_hash_id, not random rows — 70% of clients → train, 30% → test (random_state=42), so no client's pages appear on both sides. This closes the leak a random row split would allow. Time is handled by the feature engineering itself — the label window is strictly after the feature window for every row.

Train: 110,403 rows across 30 clients (base rate 33.3%). Test: 41,578 rows across 14 held-out clients (base rate 31.0%).

Base rateTest-set clients31.0%*

*Test-client-only base rate (31.0%) sits close to the whole-population figure (32.7%) — no meaningful split imbalance.

Validation-design honesty point: the Week-4 rule's 50.0% Precision@10 (Section 03) was scored on the whole month, not client-held-out. Refit on train clients only and scored on the same held-out test clients as the model, the rule collapses to 10.0% — below even the base rate. Comparing the rule's original 50.0% to the model's 40.0% directly would overstate the rule's real-world performance.

Error analysis (reading Logistic Regression, the model taken forward above):

Coefficients (direction + rough weight): clicks_first_half −0.556, impressions_first_half +0.300, active_days_first_half −0.270, avg_position_first_half −0.102, ctr_first_half +0.019.

Random Forest permutation importance (for comparison): ctr_first_half +0.0455, avg_position_first_half +0.0371, impressions_first_half +0.0349, active_days_first_half +0.0232, clicks_first_half +0.0114.

Where the model is most wrong: top-decile prediction vs actual, by tier (n≥20) — worst cases cluster in the low (<10 first-half clicks) volume tier regardless of position tier, with error rates from 39% up to 74.1% for no-data-position / low-volume pairs. The model is least reliable exactly where it has the least first-half signal to work with.

3 concrete wrong cases (flagged in the predicted top 10, did not actually decline) — all three share a pattern: high first-half impressions, near-zero CTR, and 15/15 active days, yet held steady rather than declining, likely a mid-March content change the 5 features can't see:

Section 06

Interpretation

Signal audit — tested directly on this slice
TestHypothesisVerdict
CTR vs position tierBetter position → higher CTRMIXED
Volume vs decline rateMore volume → less likely to declineMIXED
Active-day coverage vs declineMore coverage → different decline rateMIXED
Flag-linked: position vs impressionsMatches paper's portfolio r = −0.592WEAK, SAME DIRECTION

Active-day coverage: sparse (1–3 days) sits at a 5.9% decline rate, then partial/mostly/full (4–15 days) all cluster around ~30% — a step, not a clean monotonic trend. Flag-linked check: r = −0.059 (n = 150,674) vs the paper's portfolio-level r = −0.592 — same negative direction, on a different value metric and a narrower slice, but far weaker.

Two of three signals a content team might assume hold true — "better position always means better CTR," "more volume always means safer from decline" — came back MIXED on this slice, not confirmed. That's a useful finding on its own: evidence against trusting any single-signal rule, and the reason a model weighing several imperfect signals together is worth the added complexity — confirmed by the evaluation above (40.0% vs the rule's held-out 10.0%).

Section 07

Recommendation

  1. Review high_volume_at_risk-flagged pages first — most impressions at stake if the flag is right, so the highest expected-value use of limited review time.
  2. Treat thin_coverage-flagged pages as lower-confidence — fewer than 5 active days in the feature window means a noisier estimate; verify against daily-level data before acting.
  3. Never automate directly from this queue — no auto-delete, de-index, or redirect. A human checks the live page, rules out a site-wide cause, and checks for a known seasonal dip before treating a flag as content-specific.

This is decision support for March 2026, this warehouse slice, and this specific 20%-drop-vs-first-half target — not a general health score, not a claim about search-engine mechanics, and not yet validated for other months or clients.

Section 08

Reproducibility

Clone the repo, open work/notebooks/capstone.ipynb in Colab, add your own HF_TOKEN (Read token, gated-repositories permission) to Colab's Secrets panel, and Runtime → Run all. The notebook is self-contained — it rebuilds feature_frame, trains the model, and rebuilds the ranked queue inline. random_state=42 throughout. This project claims a client-grouped held-out evaluation, not a separately sealed month — the split's build cell and the metrics it produces are both committed, so the evaluation is checkable from the repo, not taken on faith.
